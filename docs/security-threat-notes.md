# Security threat notes (gateway phase)

These notes are deliberately short, not a full threat model. They cover what
the gateway addresses now, what it does not, and what comes next. There is no
authentication yet (JWT/OIDC is the next phase).

| Threat | Today | Mitigation in place | Residual risk / next step |
|---|---|---|---|
| **Direct backend access** (skipping the gateway, and with it rate limits, CORS and logs) | The backends still publish host ports (8000, 8001, 8080) for the lab's tests and tools | The gateway is the documented entry point, and the frontend uses one variable (`VITE_API_URL`) to target it | In production the backends get **no public ports**: private subnets/network policies so that only the gateway reaches them. Until auth exists at the edge, the backends trust the network. |
| **Admin API exposure** (whoever reaches it can rewrite all routing with `POST /config`) | Published on **`127.0.0.1:8089` only**, never on the LAN. It is not proxied (`/services`, `/config` on :8088 → 404, tested). The Admin GUI is off. | The route-state exporter only issues GETs | Inside `migration-network` other lab containers can reach `api-gateway:8001`, which is the same trust zone as the lab's databases with default passwords. Production: no Admin API at all (DB-less config baked into an immutable image and deployed by CI), or an admin listener bound to a management interface with mTLS. |
| **Rate-limit bypass** | `rate-limiting` at 100 req/s and 3000 req/min, `limit_by: ip`, `policy: local` | `trusted_ips` is not set, so a client-sent `X-Forwarded-For` / `X-Real-IP` **cannot** change the IP Kong limits on and logs as `client_ip` (tested) | Locally every host client shares the Docker gateway IP (one bucket). `local` is a per-node counter; with several Kong nodes use `redis`. Per-consumer limits need auth. Rotating source IPs (a botnet) needs a WAF/CDN tier. |
| **Header spoofing** | The client controls `X-Request-ID`, `traceparent` and `X-Forwarded-*` | `X-Request-ID` is accepted only if it has at most 128 chars and uses `[A-Za-z0-9._:-]`, otherwise it is replaced by a fresh UUID (`pre-function`, tested). `X-Kong-Request-Id` is not emitted. Kong **overwrites** `X-Real-IP` with the real peer, but **appends** to `X-Forwarded-For` (standard proxy behaviour, tested): only its last entry is trustworthy. | A client can still pick a *valid* request id or trace id, which is useful for correlation and not a privilege. Backends must never trust the leftmost `X-Forwarded-For` entries (none of them uses it today). Nothing authorises on these headers. When auth arrives, identity headers (`X-User-Id`...) set by the gateway must be **stripped from client requests**. |
| **CORS** | Centralised in the gateway: an explicit origin list (`http://localhost:5173`, `http://127.0.0.1:5173`), no `*`, `credentials: false` | The gateway strips the monolith's `Access-Control-Allow-Credentials`, so exactly **one** policy reaches the browser. A disallowed origin gets no `Access-Control-Allow-Origin` (tested). | CORS protects browsers, not the API; curl ignores it. Adding a frontend origin is a template change (versioned, validated in CI). |
| **DoS** | Rate limit, a 2 s connect timeout, 30 s read/write timeouts, `retries: 0` (no retry amplification), and active health checks (fast 503 instead of queueing on a dead backend) | A burst beyond 100/s gets **429 from Kong** without touching a backend (tested with 400 requests) | Slowloris-style attacks and connection floods belong to the tier in front (LB/CDN). There is no per-route budget yet. |
| **Oversized payload** | `request-size-limiting`: 1 MB (the API's real bodies are ~100 bytes) | A 2 MB POST gets **413 from Kong** and never reaches the backend (tested) | Also consider header-size and URL-length limits at the LB. |
| **Information disclosure** | `Server`/`Via` version banners removed (`KONG_HEADERS=latency_tokens` + `response-transformer`). The backend's `/docs`, `/openapi.json`, `/metrics`, `/health` and `/internal/*` are **not routed**. | Security headers: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` | `X-Upstream-Service` and `X-Kong-*-Latency` are **lab-only didactic headers** that reveal topology and timing. Remove them for production. HSTS arrives with TLS. |
| **Log leakage** | Access log (file-log) drops request/response **headers** (future `Authorization`/cookies) | request_id/trace_id are JSON fields, not Loki labels | Query strings are still logged. Revisit if PII ever goes in URLs. |
| **Unsafe route changes** | Scripts refuse write cutovers and known incompatibilities without explicit flags. Every change is verified against the runtime and recorded in `state/history.log`, and the Admin API access log is on. | The default (and boot) state is everything → monolith | Anyone with localhost access can run the scripts. In production route changes go through PR + CI (the profiles are versioned). |
